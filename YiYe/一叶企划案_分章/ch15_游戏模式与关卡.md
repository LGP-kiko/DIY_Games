## 15　游戏模式与关卡

本章定义《一叶 / One Leaf》全部可玩内容的外层框架：玩家从哪里进入一局、进入前能调整什么、内置战场长什么样、程序化战场如何被生成、4 关战役如何被编排、剧本逻辑用什么数据结构描述、一局如何结束并结算，以及结束后如何再开一局。本章所有数值均为**确定值**，实施方不得自行「视情况而定」。凡与权威章节冲突者一律服从：建筑、单位、武器数值与源质储量以第 8 章《权威数值表》为准，地图与地形（`MapData` 结构、地形编码、通行性矩阵、建造合法性）以第 5 章为准，tick / PRNG / 坐标等规范以第 2 章为准，战斗与投射物规则以第 9 章为准，AI 行为与难度参数以第 12 章为准。本章只拥有：**具体地图内容（坐标、源质矿脉位置、地形构成）、随机地图生成器、战役关卡、触发器、胜负结算、人口口径**；各图「AI 适配说明」中的参数是该地图的**覆盖值**，凡与第 12 章不同处必须显式标注「本图覆盖」。源质储量与采集/卸货速率一律采用第 8 章权威值，本章仅人口口径与计时口径为基础约定，其余章节必须复用。

三项基础约定（P0）：其一，**逻辑帧固定为 20 Hz，1 tick = 50 ms**，游戏速度档位只改变「每真实秒推进多少逻辑 tick」，不改变 tick 内部的时间粒度，因此所有触发器延迟、建造时间、护盾回复以 tick 为唯一单位书写。其二，经济口径**一律采用第 8 章权威值**：**源质矿脉每格 400 源质（`ESSENCE_PER_TILE`）、晶簇每格 800 源质（`CRYSTAL_PER_TILE`）**、采集容量 240 源质（`HARVEST_CAP`）、基准采集速率 40 源质/秒（原初 ×1.2 = 48、主宰奴役 ×1.4 = 56、侵蚀 40）、卸货速率 240 源质/秒（`UNLOAD_RATE`）；本章任何「源质总量」都由 `矿脉格数 × 400 + 晶簇格数 × 800` 得出，与随附工具 `yiye_maps.js` 的 `mapDerived()` 输出逐字一致。矿脉枯竭口径与第 6 章一致：单簇剩余总量小于 20% 时播报「矿区即将枯竭」，全部矿脉枯竭时播报「所有矿区已枯竭」。其三，**地图坐标一律使用格坐标 (x, y)，原点在左上角，x 向右递增，y 向下递增**，等距投影按 `screenX=(x-y)*32`、`screenY=(x+y)*16-z*12` 换算，因此「地图左上」在屏幕上表现为正上方偏右；**1 格 = 世界 1 单位**，不存在旧稿里「格与米」的双口径。

#### 15.1.1　模式运行时的分支点

模式差异只允许出现在 4 个分支点上（P0）。第一，**初始世界状态注入**：遭遇战与快速战斗由设置界面注入，战役由关卡的 `init` 块注入。第二，**胜负条件包装器**：战役把通用判定包在任务条件内，任务条件优先。第三，**UI 顶栏内容**：战役顶栏渲染任务目标列表，遭遇战顶栏渲染双方人口与源质对比条。第四，**AI 控制器装配**：遭遇战装配标准 AI，战役可选择装配脚本 AI（ScriptAI）或标准 AI 加触发器干预。

三条**全模式强制规则**（P0），任何模式都不得例外：其一，**混沌永不成为玩家阵容**——`CHAOS` 只能在战役第 1 关之类的地图里充当脚本敌方，遭遇战与快速战斗的阵容下拉框中不出现该选项；其二，**战争单位不受任何正负面特殊效果**——老兵、护盾、再生、吞噬、腐蚀、解放对 `py_wrath`、`dm_warlord`、`er_core_unit` 一律不生效；其三，**奴隶不占人口**——主宰的 `dm_slave`、以及被解放后的奴隶，都不计入任何一方的人口上限。

### 15.3　地图系统总览

地图数据的唯一权威结构为 `MapData`（P0，与第 5 章 5.7 完全一致）。必需字段：`id`、`name`、`size`（`[w, h]`）、`symmetry`（取值只能是 `point` / `mirror_x` / `mirror_y` / `none`）、**四个平铺数组** `terrain`（长度 `size*size` 的 Uint8Array，存地形枚举）、`height`（同长度 Uint8Array，存 **0 至 4** 的层高）、`essence`（同长度 Uint16Array，存每格剩余源质，非矿脉格必须为 0）、`pass`（同长度 Uint8Array，存本局静态通行位掩码，由地形与层高在开局一次性烘焙，供流场寻路复用）、`spawns`（数组，每项含 `faction`、`x`、`y`、`facing`）；可选字段：`oreFields`（源质矿点摘要，仅供校验与 AI 决策）、`chaosLairs`（混沌巢穴数组，每项含 `x`、`y`、`scale`）、`triggers`（数组）、`brief`（一句话战术说明）。**地形数组一律命名为 `terrain`（不再叫 `tiles`），且必须携带 `essence` 储量数组；`neutralPoints`、`aiHints` 等自定义字段作废——中立资源点由 `oreFields` 的坐标表达，混沌巢穴由 `chaosLairs` 表达，AI 行为提示由本章各图的「AI 适配说明」与第 12 章的 AI 档案表达。** 地形枚举在 `terrain` 中为 0 至 11 的整数（**权威编码见下表**；ASCII 字符中的 `1`/`2` 仅表示出生点标记、`C` 仅表示混沌巢穴标记，都不是地形枚举），ASCII 示意图只是人类可读的投影。

### 15.5　程序化随机地图生成器

快速战斗模式使用程序化生成器。生成器必须**确定性**：同一 `(seed, size, symmetry)` 三元组必须产生逐格完全一致的地图（P0）。生成器输出一个合法的 `MapData`（字段与第 5 章 5.7 一致，即 `terrain` / `height` / `essence` / `pass` 四个平铺数组加 `id`、`name`、`size`、`symmetry`、`spawns`、`oreFields`、`chaosLairs`、`triggers`、`brief`），其中 `triggers` 为空数组、`oreFields` 与 `chaosLairs` 由生成器按实际结果写入。

生成流水线共 8 步，顺序固定，不得交换（P0）：

1. 种子初始化与 PRNG 构造
2. 对称骨架选择
3. 地形噪声铺设
4. 毒瘴与叶底裂隙侵蚀
5. 源质矿脉与晶簇布置
6. 出生点选址与校验
7. 连通性校验
8. 公平性校验

#### 15.5.1　步骤 1：种子初始化与 PRNG

使用 32 位 xorshift128 变体，禁止使用 `Math.random()`（P0）。种子为空或非法时，用 `Date.now() & 0xFFFFFFFF` 兜底，并把实际使用的种子回写进设置界面，保证玩家可复现。生成器使用的随机流固定为第 16 章的 `map` 流（`streamSeed = (masterSeed ^ 0x9E3779B9) >>> 0`），**不得占用 `combat` 与 `ai` 流**，否则同一存档在重开时的战斗判定会被地图生成平移。

```js
// P0：确定性 PRNG，state 由 seed 派生（与本生成器专用，不复用第 16 章的运行时流）
function makeRng(seed) {
  let s0 = (seed ^ 0x9E3779B9) >>> 0;
  let s1 = (seed ^ 0x85EBCA6B) >>> 0;
  let s2 = (seed ^ 0xC2B2AE35) >>> 0;
  let s3 = (seed ^ 0x27D4EB2F) >>> 0;
  function next() {
    let t = s0 ^ (s0 << 11);
    s0 = s1; s1 = s2; s2 = s3;
    s3 = (s3 ^ (s3 >>> 19)) ^ (t ^ (t >>> 8));
    return s3 >>> 0;
  }
  return {
    next,
    int(min, max) { return min + (next() % (max - min + 1)); }, // 闭区间
    float() { return next() / 4294967296; },
    chance(p) { return this.float() < p; },
    pick(arr) { return arr[this.int(0, arr.length - 1)]; }
  };
}
```

#### 15.5.2　步骤 2：对称骨架

骨架决定地图的宏观公平性。生成器先按设置或随机选择一种对称方式，再据此确定出生点方位。

| 骨架类型 | 出现权重 | 出生点方位 | 对称映射（96×96） | 适用尺寸 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| point | 50% | 对角 | (x,y) 到 (95-x, 95-y) | 全部 | P0 |
| mirror_x | 25% | 东西 | (x,y) 到 (95-x, y) | 全部 | P0 |
| mirror_y | 25% | 南北 | (x,y) 到 (x, 95-y) | 全部 | P0 |

骨架选定后，生成器只计算地图的**四分之一或二分之一**区域，其余区域由对称映射复制（P0）。对 `point` 骨架，只生成 x 小于 n/2 且 y 小于 n/2 的象限，以及 x 与 y 交叉的中轴带的一半，再镜像两次。这样做既省算力，也从数学上保证两侧绝对对称。

```js
// P0：骨架与镜像复制（symmetry 只有 point / mirror_x / mirror_y / none 四种取值）
function applySymmetry(terrain, height, essence, n, sym) {
  const at = (x, y) => y * n + x;
  for (let y = 0; y < n; y++) {
    for (let x = 0; x < n; x++) {
      if (sym === "none") continue; // 无对称：整图独立生成，不做复制
      if (sym === "point" && (x >= n / 2 || y >= n / 2)) continue;
      if (sym === "mirror_x" && x >= n / 2) continue;
      if (sym === "mirror_y" && y >= n / 2) continue;
      let mx, my;
      if (sym === "point") { mx = n - 1 - x; my = n - 1 - y; }
      else if (sym === "mirror_x") { mx = n - 1 - x; my = y; }
      else { mx = x; my = n - 1 - y; } // mirror_y
      terrain[at(mx, my)] = terrain[at(x, y)];
      height[at(mx, my)] = height[at(x, y)];
      essence[at(mx, my)] = essence[at(x, y)]; // 储量数组必须与地形一同镜像
    }
  }
  // 中轴带单独处理，保证 (n/2-1, n/2-1) 与 (n/2, n/2) 等中心格自洽
  return { terrain, height, essence };
}
```

#### 15.5.3　步骤 3：地形噪声铺设

地形噪声分三层叠加（P0）：低频「生物群系」层决定叶肉、腐土、灰沙的大块分布；中频「斑块」层制造 6 至 14 格的杂色斑；高频「颗粒」层以 8% 概率逐格抖动。三层都使用值噪声，采样频率与权重见下表。**旧稿的 grass / dirt / sand 三件套作废**：新地形映射的目标是 `flesh` 叶肉 / `rot` 腐土 / `ash` 灰沙 / `strata` 岩层 四种，毒瘴与叶底裂隙由步骤 4 的脊线侵蚀单独负责，孢子林由步骤 4 之后的撒点负责。

| 层 | 采样频率 | 权重 | 作用 | 目标占比结果 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| 低频 | 1/28 | 0.62 | 决定叶肉与腐土的大块边界 | flesh 50 至 62% | P0 |
| 中频 | 1/9 | 0.27 | 制造斑块，避免大色块 | rot 6 至 12% | P0 |
| 高频 | 1/3 | 0.11 | 逐格抖动，制造灰沙碎点 | ash 3 至 15% | P0 |

```js
// P0：三层值噪声，输出 0 至 1
function terrainNoise(rng, n, noiseSeed) {
  const grid = {};
  function lattice(freq, gx, gy) {
    const k = freq + ":" + gx + ":" + gy;
    if (grid[k] === undefined) {
      const r = makeRng((noiseSeed ^ (gx * 73856093) ^ (gy * 19349663) ^ (freq * 83492791)) >>> 0);
      grid[k] = r.float();
    }
    return grid[k];
  }
  function sample(freq, x, y) {
    const fx = x / freq, fy = y / freq;
    const x0 = Math.floor(fx), y0 = Math.floor(fy);
    const tx = fx - x0, ty = fy - y0;
    const sx = tx * tx * (3 - 2 * tx), sy = ty * ty * (3 - 2 * ty);
    const a = lattice(freq, x0, y0), b = lattice(freq, x0 + 1, y0);
    const c = lattice(freq, x0, y0 + 1), d = lattice(freq, x0 + 1, y0 + 1);
    return (a * (1 - sx) + b * sx) * (1 - sy) + (c * (1 - sx) + d * sx) * sy;
  }
  const out = new Float32Array(n * n);
  for (let y = 0; y < n; y++) {
    for (let x = 0; x < n; x++) {
      const v = 0.62 * sample(28, x, y) + 0.27 * sample(9, x, y) + 0.11 * sample(3, x, y);
      out[y * n + x] = v;
    }
  }
  return out;
}
```

推荐占比与实际噪声输出的对应关系（P0）：噪声值小于 0.30 映射为 `rot` 腐土，0.30 至 0.36 映射为 `ash` 灰沙，0.36 至 0.88 映射为 `flesh` 叶肉，大于 0.88 映射为 `strata` 岩层。映射后若某地形占比超出下表容差，生成器按「就近替换」原则反复调整阈值，最多迭代 12 次。

| 地形 | 目标占比 | 允许容差 | 超差处理 | 优先级 |
| --- | --- | --- | --- | --- |
| flesh 叶肉 | 52% | 正负 6% | 调整 strata 阈值上下界 | P0 |
| rot 腐土 | 9% | 正负 4% | 调整 ash 阈值 | P0 |
| ash 灰沙 | 5% | 正负 3% | 调整 flesh 阈值 | P1 |
| strata 岩层 | 8% | 正负 4% | 直接增删随机岩块 | P0 |
| spore 孢子林 | 4% | 正负 2% | 在 flesh 上随机撒点 | P0 |

#### 15.5.4　步骤 4：毒瘴与叶底裂隙侵蚀

毒瘴与叶底裂隙都由「脊线」生成（P0）。生成器先随机放置 1 至 3 条脊线（毒瘴 1 至 2 条，叶底裂隙 0 至 2 条），每条脊线是一条由 5 至 9 个控制点连成的折线，控制点坐标由 PRNG 在四分之一地图内采样。随后以脊线为中心按宽度参数做膨胀，再过对称映射复制。

**两条关键差异（P0）**：其一，脊线侵蚀出的地形从旧稿的 `water` / `cliff` 改为 **`miasma` 毒瘴（编码 5）** 与 **`rift` 叶底裂隙（编码 7）**；其二，毒瘴上的过河通道不再一律改成浅滩，而是**交替生成 浅毒滩（`shallow`，编码 6）与 岩桥（`bridge`，编码 10）**，前者只对 `foot` 与 `hover` 开放，后者对全部地面移动类型开放——这正是「载具只能走岩桥、步兵才能涉浅毒滩」的地图级实现。

| 参数 | 取值范围 | 默认值 | 说明 | 优先级 |
| --- | --- | --- | --- | --- |
| 毒瘴脊线数 | 1 至 2 | 1 | 0 条时地图无任何毒瘴 | P0 |
| 毒瘴宽度 | 6 至 14 格 | 9 | 正交方向上单侧宽度 | P0 |
| 毒瘴端点留边 | 8 格 | 8 | 脊线端点距地图边缘的最小距离 | P0 |
| 浅毒滩带宽度 | 3 至 5 格 | 4 | 毒瘴与陆地之间的过渡带 | P0 |
| 跨越通道数 | 2 至 3 | 2 | 毒瘴被通道打断的次数 | P0 |
| 通道宽度 | 8 至 12 格 | 10 | 每条通道的净宽 | P0 |
| 通道类型 | 交替 | 交替 | 第 1 条通道铺浅毒滩，第 2 条铺岩桥，第 3 条再铺浅毒滩 | P0 |
| 裂隙脊线数 | 0 至 2 | 1 | 脊线两侧高度差 1 层 | P0 |
| 裂隙宽度 | 2 至 4 格 | 3 | 裂隙立面的水平厚度 | P1 |
| 坡道数 | 每脊线 2 至 4 | 3 | 打断裂隙的位置数，缺口铺 `vein` | P0 |
| 坡道宽度 | 6 至 10 格 | 8 | 每条坡道的净宽 | P0 |

```js
// P0：脊线膨胀为毒瘴或叶底裂隙，并打断出通道（同时清零被改格上的储量）
function carveRidge(terrain, height, essence, n, rng, opts) {
  const pts = [];
  const cnt = rng.int(5, 9);
  for (let i = 0; i < cnt; i++) {
    pts.push({
      x: rng.int(opts.margin, n / 2 - 1),
      y: rng.int(opts.margin, n - 1 - opts.margin)
    });
  }
  const half = Math.floor(opts.width / 2);
  for (let i = 0; i < pts.length - 1; i++) {
    const a = pts[i], b = pts[i + 1];
    const steps = Math.max(Math.abs(b.x - a.x), Math.abs(b.y - a.y));
    for (let s = 0; s <= steps; s++) {
      const cx = Math.round(a.x + (b.x - a.x) * s / steps);
      const cy = Math.round(a.y + (b.y - a.y) * s / steps);
      for (let dy = -half; dy <= half; dy++) {
        for (let dx = -half; dx <= half; dx++) {
          const x = cx + dx, y = cy + dy;
          if (x < 0 || y < 0 || x >= n || y >= n) continue;
          const k = y * n + x;
          if (opts.kind === "miasma") terrain[k] = 5;              // 毒瘴
          else { terrain[k] = 7; height[k] = 1; }                  // 叶底裂隙，抬高 1 层
          essence[k] = 0; // 毒瘴与裂隙格不允许残留储量
        }
      }
    }
  }
  // 在毒瘴上开通道：交替铺浅毒滩与岩桥
  if (opts.kind === "miasma") {
    const holes = rng.int(opts.minCross, opts.maxCross);
    const used = [];
    for (let h = 0; h < holes; h++) {
      let cx, tries = 0;
      do { cx = rng.int(opts.margin, n - 1 - opts.margin); tries++; }
      while (used.some(u => Math.abs(u - cx) < opts.crossWidth * 2) && tries < 40);
      used.push(cx);
      const crossKind = (h % 2 === 0) ? 6 : 10;   // 偶数条浅毒滩，奇数条岩桥
      for (let y = 0; y < n; y++) {
        for (let dx = -Math.floor(opts.crossWidth / 2); dx <= Math.floor(opts.crossWidth / 2); dx++) {
          const x = cx + dx;
          if (x < 0 || x >= n) continue;
          const k = y * n + x;
          if (terrain[k] === 5) terrain[k] = crossKind;
        }
      }
    }
  }
  // 在叶底裂隙上开坡道：缺口铺 vein（唯一可作坡道的地形）
  if (opts.kind === "rift") {
    for (let r = 0; r < opts.rampCount; r++) {
      const cx = rng.int(opts.margin, n - 1 - opts.margin);
      for (let y = 0; y < n; y++) {
        for (let dx = -Math.floor(opts.rampWidth / 2); dx <= Math.floor(opts.rampWidth / 2); dx++) {
          const x = cx + dx;
          if (x < 0 || x >= n) continue;
          const k = y * n + x;
          if (terrain[k] === 7) { terrain[k] = 3; height[k] = 0; }  // vein 坡道
        }
      }
    }
  }
  return { terrain, height, essence };
}
```

#### 15.5.5　步骤 5：矿脉布置

源质布置遵循「先主矿后副矿再晶簇」的顺序（P0）。主矿必须落在距某个出生点 8 至 16 格、且四周至少 4 格为可建造地形的区域；副矿落在距双方出生点均大于 24 格的区域；晶簇最多 3 处，落在距双方出生点均大于 30 格的区域，且**至少 1 处必须落在混沌巢穴 6 格半径内**，以复现内置地图「富矿在巢穴脚下」的设计。所有矿点随后由对称映射复制到对侧。

| 矿点类型 | 数量 | 单点格数 | 距离出生点 | 落点地形要求 | 折合源质 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| 主矿 | 每方 1 处 | 36 至 56 格 | 8 至 16 格 | 全为 `flesh` 或 `rot` | 14400 至 22400 | P0 |
| 副矿 | 每方 1 至 2 处 | 24 至 48 格 | 24 至 48 格 | 全为 `flesh` 或 `rot` | 9600 至 19200 | P0 |
| 中立矿 | 2 至 4 处 | 24 至 48 格 | 双方均大于 24 格 | 全为 `flesh` 或 `rot` | 9600 至 19200 | P1 |
| 晶簇 | 0 至 3 处 | 4 至 16 格 | 双方均大于 30 格 | 全为 `flesh` 或 `rot` | 3200 至 12800 | P1 |
| 装饰矿 | 0 至 2 处 | 6 至 12 格 | 无限制 | 允许 `ash` | 2400 至 4800 | P2 |

上表「折合源质」列按第 8 章权威值换算：矿脉 `格数 × 400`、晶簇 `格数 × 800`，因此主矿 36 至 56 格即 14400 至 22400 源质，晶簇 4 至 16 格即 3200 至 12800 源质。

```js
// P0：在满足地形与距离约束的位置放置源质，并写入储量数组
const ESSENCE_PER_TILE = 400;   // 第 8 章权威值
const CRYSTAL_PER_TILE = 800;   // 第 8 章权威值

function placeOreField(terrain, essence, n, cx, cy, w, h, kind) {
  const oreId = kind === "crystal" ? 9 : 8;   // 8 = essence 源质矿脉, 9 = crystal 晶簇
  const perTile = kind === "crystal" ? CRYSTAL_PER_TILE : ESSENCE_PER_TILE;
  for (let dy = 0; dy < h; dy++) {
    for (let dx = 0; dx < w; dx++) {
      const x = cx + dx, y = cy + dy;
      if (x < 1 || y < 1 || x >= n - 1 || y >= n - 1) return false;
      const t = terrain[y * n + x];
      if (t !== 0 && t !== 1) return false;  // 仅允许 flesh 与 rot 作为底材
      // 不贴毒瘴与浅毒滩
      if (terrain[(y + 1) * n + x] === 5 || terrain[(y - 1) * n + x] === 5) return false;
      if (terrain[y * n + x + 1] === 6 || terrain[y * n + x - 1] === 6) return false;
    }
  }
  for (let dy = 0; dy < h; dy++) {
    for (let dx = 0; dx < w; dx++) {
      const k = (cy + dy) * n + cx + dx;
      terrain[k] = oreId;
      essence[k] = perTile;   // 每格储量：矿脉 400，晶簇 800
    }
  }
  return true;
}
```

#### 15.5.6　步骤 6：出生点选址与校验

出生点不再随机，而是由骨架直接决定（P0）：`point` 骨架取 (m, m) 与 (n-1-m, n-1-m)；`mirror_x` 取 (m, n/2) 与 (n-1-m, n/2)；`mirror_y` 取 (n/2, m) 与 (n/2, n-1-m)。其中 `m` 在 10 至 18 之间随机，`n` 为 64 时 `m` 上限为 14。选址后立即执行五项校验，任一失败则原地微调 3 格并重试，最多 20 次；仍失败则重掷 `m`，再失败则整图重生成（最多 5 次）。

| 校验项 | 判定条件 | 失败处理 | 优先级 |
| --- | --- | --- | --- |
| 可建造面积 | 出生点周围 8×8 格内至少有 40 格为 `flesh` 或 `rot` | 向地图几何中心方向平移 3 格重试 | P0 |
| 平坦度 | 出生点周围 8×8 格内 height 全为 0 | 平移 3 格重试，仍失败则清除该区域裂隙 | P0 |
| 通行可达 | 从出生点出发存在到地图几何中心的 8 邻域路径（`foot` 与 `track` 各判定一次） | 触发步骤 7 的修复流程 | P0 |
| 初始视野 | 出生点周围 12 格内无对方出生点 | 增大 `m`，重掷 | P0 |
| 巢穴距离 | 出生点到最近混沌巢穴的 8 向路径长度大于等于 24 格 | 把该巢穴沿向量外移 4 格 | P0 |

#### 15.5.7　步骤 7：连通性校验

连通性校验是本生成器最关键的一步（P0）。校验必须**按通行类型分别执行两遍**：先按 `foot`（步兵）通行性校验一次，再按 `track`（履带，轮式共用同一口径）通行性校验一次，两遍都必须通过（与第 5 章 5.3 通行性矩阵、5.7 地图校验规则一致）。可通行格不再使用单一集合：`foot` 可走 `flesh`、`rot`、`ash`、`vein`、`shallow`、`essence`、`crystal`、`bridge`，并且在高差为 1 时可爬 `rift`（速度 ×0.6），高差 ≥2 时不可通行；`track` / `wheel` 只可走 `flesh`、`rot`、`ash`、`vein`、`essence`、`crystal`、`bridge`，**不可通行 `shallow` 与 `rift`**，且只允许高差为 0 的相邻格。两遍校验各自的目标有三个：其一，双方出生点在该通行类型下必须互相可达；其二，每一个矿脉格与晶簇格的**至少一个相邻格**必须可达；其三，地图上任何面积大于 400 格的可通行连通块都必须与主连通块相连，否则该块被判定为「孤岛」并回填为 `strata`。

**`hover` 的说明（P0）**：`hover` 是第 5 章的第四种地面移动类型，可通行 `flesh`、`rot`、`ash`、`vein`、`miasma`、`shallow`、`essence`、`crystal`、`bridge`，不可通行 `strata`、`rift`、`spore`。按本章要求，**连通性校验只需按 `foot` 与 `track` 两套各校验一次**；`hover` 的通行性由第 5 章矩阵保证，生成器不为其单独做连通性断言，但必须在生成的 `pass` 位掩码中正确写入。

```js
// P0：按通行类型分别做洪水填充连通性校验（与第 5 章 5.3 通行性矩阵一致）
const FOOT_OK   = new Set([0, 1, 2, 3, 6, 7, 8, 9, 10]); // flesh,rot,ash,vein,shallow,rift,essence,crystal,bridge
const TRACK_OK  = new Set([0, 1, 2, 3, 8, 9, 10]);        // 不含 shallow 与 rift；wheel 共用同一口径
const HOVER_OK  = new Set([0, 1, 2, 3, 5, 6, 8, 9, 10]);  // 含 miasma 与 shallow，不含 rift；仅用于烘焙 pass 位掩码
const GROUND_MOVES = ["foot", "track"];

// 相邻两格是否可通行：高差 ≥2 时全部地面单位不可通行；foot 额外允许高差 1（速度 ×0.6）
function canStep(terrain, height, from, to, move) {
  const t = terrain[to];
  const dh = Math.abs(height[to] - height[from]);
  if (dh >= 2) return false;
  if (move === "foot") return FOOT_OK.has(t) && dh <= 1;
  return TRACK_OK.has(t) && dh === 0;
}

function floodFill(terrain, height, n, sx, sy, move, allowed) {
  const label = new Int32Array(n * n).fill(-1);
  const queue = new Int32Array(n * n);
  let head = 0, tail = 0, comp = 0;
  const comps = [];
  for (let y = 0; y < n; y++) {
    for (let x = 0; x < n; x++) {
      const k = y * n + x;
      if (label[k] !== -1 || !allowed.has(terrain[k])) continue;
      let size = 0;
      label[k] = comp; queue[tail++] = k;
      while (head < tail) {
        const c = queue[head++];
        size++;
        const cx = c % n, cy = (c / n) | 0;
        for (let dy = -1; dy <= 1; dy++) {
          for (let dx = -1; dx <= 1; dx++) {
            if (dx === 0 && dy === 0) continue;
            const nx = cx + dx, ny = cy + dy;
            if (nx < 0 || ny < 0 || nx >= n || ny >= n) continue;
            const nk = ny * n + nx;
            if (label[nk] !== -1 || !allowed.has(terrain[nk])) continue;
            if (!canStep(terrain, height, c, nk, move)) continue;
            label[nk] = comp; queue[tail++] = nk;
          }
        }
      }
      comps.push({ id: comp, size, seedX: x, seedY: y });
      comp++;
    }
  }
  const startLabel = label[sy * n + sx];
  return { label, comps, startLabel };
}

// P0：foot 与 track 各校验一次，任何一套不通过都判定为连通性失败
function validateConnectivity(terrain, height, n, spawns, oreFields) {
  const results = {};
  for (const move of GROUND_MOVES) {
    const allowed = move === "foot" ? FOOT_OK : TRACK_OK;
    const fill = floodFill(terrain, height, n, spawns[0].x, spawns[0].y, move, allowed);
    const okSpawns = spawns.every(s => fill.label[s.y * n + s.x] === fill.startLabel);
    const okOre = oreFields.every(f => f.tiles.some(([x, y]) =>
      fill.label[y * n + x] === fill.startLabel ||
      [[1, 0], [-1, 0], [0, 1], [0, -1]].some(([dx, dy]) =>
        fill.label[(y + dy) * n + (x + dx)] === fill.startLabel)));
    results[move] = { fill, ok: okSpawns && okOre };
  }
  return { results, ok: results.foot.ok && results.track.ok };
}
```

#### 15.5.8　步骤 8：公平性校验

公平性校验在连通性通过后执行（P0）。校验分三项：资源公平、路程公平、地形公平。

| 校验项 | 判定公式 | 通过阈值 | 失败处理 | 优先级 |
| --- | --- | --- | --- | --- |
| 资源公平 | 两侧可达源质总量之差的绝对值除以平均值 | 小于等于 5% | 从富侧随机移除若干矿格，补给贫侧等量矿格 | P0 |
| 单矿公平 | 双方主矿格数之差 | 小于等于 4 格 | 削平较大主矿 | P0 |
| 路程公平 | 双方出生点到最近中立矿的路径长度之差 | 小于等于 8 格 | 移动该中立矿 4 格 | P0 |
| 晶簇公平 | 双方到最近晶簇的路径长度之差 | 小于等于 10 格 | 移动或删除晶簇 | P1 |
| 巢穴公平 | 双方出生点到最近混沌巢穴的路径长度之差 | 小于等于 6 格 | 移动较近的那个巢穴 4 格 | P0 |
| 地形公平 | 双方出生点 24 格半径内可建造格数之差除以平均值 | 小于等于 8% | 在贫侧补填 `strata` 为 `flesh` | P1 |

```js
// P0：资源公平校验与修复，返回是否通过
function checkResourceFairness(map, n) {
  const total = side => side.reduce((s, f) => s + f.cells * (f.kind === "crystal" ? CRYSTAL_PER_TILE : ESSENCE_PER_TILE), 0);
  const a = total(reachableOre(map, map.spawns[0]));
  const b = total(reachableOre(map, map.spawns[1]));
  const diff = Math.abs(a - b) / ((a + b) / 2);
  if (diff <= 0.05) return { ok: true, a, b, diff };
  const rich = a > b ? map.spawns[0] : map.spawns[1];
  const poor = a > b ? map.spawns[1] : map.spawns[0];
  const need = Math.ceil(Math.abs(a - b) / 2 / ESSENCE_PER_TILE);
  stripOreNearest(map, rich, need);
  addOreNearest(map, poor, need);
  return { ok: false, a, b, diff, repaired: true };
}
```

#### 15.6.1　第 1 关 初醒

#### 15.6.4　第 4 关 叶底之门

本关的剧本威胁是**原初的吞噬成长**：甲壳巨兽（`py_carapace`）与翼兽（`py_wing`）可以吞噬体力小于等于 25% 的混沌单位，每次永久 +10% 最大体力与 +1 轻型护甲（上限 5，最多 3 次）。地图上有 3 处混沌巢穴，其中中央巢穴倍率高达 **1.50×**，一旦原初用战争单位把混沌单位打到残血再吞噬，就能在决战前把甲壳巨兽的体力从 820 推到 1066、轻型护甲从 3 推到 5。因此玩家的**挑战目标**是「在决战前清除中央混沌领主」，抢在原初之前把中央巢穴清掉，毁掉它的养成路线。

### 15.7　触发器系统 DSL

战役与地图脚本共用同一套触发器系统。触发器是纯数据（P0），不使用 `eval`，不使用函数回调，全部逻辑由 **21 种条件类型与 24 种动作类型**的解释器实现（数量与下文两张枚举表的实际行数完全一致）。

| 字段 | 类型 | 必填 | 默认值 | 说明 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| id | 字符串 | 是 | 无 | 触发器唯一键名，同一地图内不可重复 | P0 |
| priority | 整数 | 否 | 100 | 越小越先检查，范围 0 至 999 | P0 |
| once | 布尔 | 否 | true | 为真时触发一次后不再检查 | P0 |
| maxFires | 整数 | 否 | 1 | 最多触发次数，与 once 同时存在时取较小值 | P1 |
| cooldown | 整数 | 否 | 0 | 两次触发之间至少间隔的 tick 数 | P1 |
| condition | 对象 | 是 | 无 | 条件树，见条件类型枚举 | P0 |
| actions | 数组 | 是 | 无 | 动作列表，按顺序执行，上限 24 项 | P0 |
| enabled | 布尔 | 否 | 真 | 为假时本触发器完全不参与检查 | P1 |

#### 15.7.1　执行顺序与触发语义

执行语义共 7 条，全部为 P0：

- **检查频率**：触发器系统在每个逻辑 tick 的**固定阶段**运行，顺序为「世界更新、触发器检查、动作执行、渲染快照」，因此同一 tick 内生成的单位不会在本 tick 被条件统计到。
- **执行顺序**：每 tick 把所有 `enabled` 为真的触发器按 `priority` 升序排序，`priority` 相同时按 `id` 的字典序升序；逐个求值条件，命中者立即执行动作。
- **只触发一次**：`once` 为真（默认）时，触发器首次命中后把内部 `fired` 置为真，此后每 tick 跳过条件求值，**永不再次触发**。
- **重复触发**：`once` 为假时，受 `maxFires` 与 `cooldown` 约束；`maxFires` 为 0 表示无限次；`cooldown` 以 tick 为单位，从上次执行完毕的那一 tick 起算。
- **动作原子性**：同一触发器的 `actions` 数组在同一个 tick 内按数组下标顺序串行执行；入队型动作（`spawn_units`、`spawn_building`、`spawn_slaves`、`spawn_chaos_lair`、`liberate_units`、`salvage_corpse`、`end_mission`）不立即改写世界，而是写入本 tick 的**待提交队列**，在该触发器全部动作执行完毕后统一提交，避免同一触发器内后续条件受前序动作影响。
- **动作上限**：单个触发器的 `actions` 最多 24 项；单张地图的触发器最多 256 个；单 tick 内最多执行 32 个触发器的动作，超出者顺延到下一 tick，并按 `priority` 决定顺延顺序。
- **失败隔离**：任一动作的参数校验失败（例如 `spawn_units` 的坐标越界或落在 `strata`、`spore`、`miasma` 等不可通行地形上）时，该动作被跳过并写入诊断日志，**不影响同一触发器的其余动作**，也不影响其他触发器。

### 15.8　胜负判定与结算

胜负判定在每个逻辑 tick 的「世界更新」阶段结束时执行一次（P0）。判定分三层：第一层是**彻底消灭**判定，第二层是**生产体系瓦解**判定，第三层是**超时**判定。三层按顺序求值，先命中者生效。

**第一层：彻底消灭（P0）**。某方的建筑数与单位数同时为 0 时，该方立即失败。这是最根本的胜负条件，全部模式共用。

**第二层：生产体系已瓦解（P0，新增）**。若某方**建筑数与一般单位、建筑单位、战争单位的数量同时为 0，只剩下奴役单位**（主宰的 `dm_slave`，或侵蚀通过其他途径持有的奴隶），则判定为「生产体系已瓦解」。这一判定的意义在于：奴役单位仅执行预设 AI 逻辑、玩家不可直接控制、不会建造、不会生产、不会扩张，因此「只剩奴隶」的状态在数学上已经不可能翻盘——**它允许提前结算，不必等玩家把地图上剩下的几十名奴隶一个个点掉**。判定命中后，先播报「敌方生产体系已瓦解，仅剩无法作战的奴役单位」，100 tick（5 秒）后按失败结算。**该判定不适用于混沌**——混沌本身就是「不建造、不生产、不扩张」的中立生物，其巢穴被清空后的残存单位按第一层判定处理。

```js
// P0：通用胜负判定，返回 null 或结算结果
const COLLAPSE_HOLD_TICKS = 100;   // 生产体系瓦解的播报缓冲
const SURVEY_INTERVAL = 100;

// 奴役单位集合：只有这些单位不算「生产体系」
const SLAVE_UNITS = { dm_slave: true };

// 判断某方是否只剩下奴役单位（建筑数、一般单位数、建筑单位数、战争单位数同时为 0）
function onlySlavesLeft(p) {
  if (p.buildings.some(b => !b.dead)) return false;
  return p.units.every(u => u.dead || SLAVE_UNITS[u.type] === true);
}

function evaluateMatchEnd(world) {
  const P = world.players;   // [0] 与 [1] 为初始双方；世界阵容为 PRIMORDIAL / DOMINATOR / EROSION / CHAOS
  for (const p of P) {
    const aliveBuildings = p.buildings.filter(b => !b.dead);
    const aliveUnits = p.units.filter(u => !u.dead);
    if (aliveBuildings.length === 0 && aliveUnits.length === 0) {
      return { result: p.isPlayer ? "lose" : "win", reason: "annihilation", loser: p.id };
    }
    // 第二层：生产体系已瓦解（只剩奴役单位）
    if (onlySlavesLeft(p)) {
      if (p.collapseTick === 0) {
        p.collapseTick = world.tick;
        broadcast(p.isPlayer ? "我方生产体系已瓦解，仅剩奴役单位" : "敌方生产体系已瓦解，仅剩奴役单位");
      }
      if (world.tick - p.collapseTick >= COLLAPSE_HOLD_TICKS) {
        return { result: p.isPlayer ? "lose" : "win", reason: "production_collapsed", loser: p.id };
      }
    } else {
      p.collapseTick = 0;
    }
  }
  // 第三层：超时（仅当关卡或设置声明了超时上限）
  const cap = world.timeLimitTicks;
  if (cap > 0 && world.tick >= cap) {
    const sa = combatScore(P[0]), sb = combatScore(P[1]);
    if (Math.abs(sa - sb) / Math.max(1, (sa + sb) / 2) < 0.10) {
      return { result: "draw", reason: "timeout" };
    }
    return { result: sa > sb ? "lose" : "win", reason: "timeout_points" };
  }
  return null;
}

// 战力分：建筑权重乘血量比例，加上单位造价百分之一乘血量比例
function combatScore(p) {
  const bw = { py_core: 100, py_maw: 80, py_hatch: 40, py_beast: 90, py_evolve: 90,
               py_spike: 30, py_spore: 40, py_pulse: 60, py_regen: 50, py_devour: 60,
               dm_core: 100, dm_reactor: 40, dm_extract: 80, dm_foundry: 40, dm_heavy: 90,
               dm_lab: 90, dm_sentry: 30, dm_aegis: 40, dm_radar: 60, dm_shield: 60,
               dm_recycler: 50, er_core: 100, er_maw: 80, er_spawn: 40, er_aberr: 90,
               er_corrupt: 90, er_acidvent: 30, er_cloud: 40, er_tendril: 60,
               er_furnace: 50, er_assimil: 70, ch_lair: 0 };
  let s = 0;
  for (const b of p.buildings) if (!b.dead) s += (bw[b.type] || 20) * (b.hp / b.maxHp);
  for (const u of p.units) if (!u.dead) s += u.cost * 0.01 * (u.hp / u.maxHp);
  return s;
}
```

**关于奴役单位的战场价值（P0）**：`dm_slave` 的造价为 0、人口为 0，`combatScore` 中它贡献 0 分（`u.cost * 0.01 = 0`），因此在超时平局判定中「只剩奴隶」的一方战力分必然接近 0，即使第二层判定因为某种原因未命中，第三层的超时分差判定也会把它判负。两条路径结论一致，不会出现「靠 50 个奴隶拖平局」的漏洞。

生产体系瓦解判定必须给出**明确的玩家反馈**（P0）：当对手满足条件时，先播报「敌方生产体系已瓦解，仅剩无法作战的奴役单位」，并在 100 tick（5 秒）后判定胜利，让玩家看到结果；当玩家自己满足条件时，先播报「我方已无生产建筑与一般单位，仅剩奴役单位」，100 tick 后判定失败。这一延迟用于避免「最后一台载具刚好在造」这类边界情况被误判。

超时平局的门槛为**双方战力分差小于 10%**（P0）。战力分 `combatScore` 按上表的建筑权重乘血量比例，加上单位造价的百分之一乘血量比例求和。分差大于等于 10% 时，分数高的一方判胜。

### 15.9　人口与部队上限

人口是限制部队规模的唯一硬约束（P0）。人口口径固定采用第 8 章权威数值：**步兵占 1、采集与载具占 2 至 3、战争单位占 6、建筑占 0**。人口按方独立计算，实时值等于该方全部存活单位的人口之和；训练中的单位在进入生产队列时**立即预占人口**，取消训练或单位被摧毁时立即释放，避免出现「队列里排了 20 个兵却只扣了 4 点人口」的漏洞。

**奴隶不占人口（P0，主宰的核心优势，必须写明）**：奴隶 `dm_slave` 的人口为 **0**。它由主宰的矿产中心（`dm_extract`）每 20 秒自动生成 1 名，**不占人口、不花源质、不可被玩家直接控制**，仅执行预设 AI 逻辑（自动寻找最近的源质矿脉、采集、返回卸矿）。这意味着主宰可以在人口上限 100 的配置下，同时拥有 40 台主战坦克（每台 3 人口，合计 120——实际受上限约束为 33 台加少量步兵）和一支 20 人以上的采集队伍，而对手原初的每一名拾荒者都要吃掉 2 点人口。**这是主宰在长局中唯一的结构性吃分点，任何实现都不得给奴隶加上人口消耗。**被解放后的奴隶仍然不占人口，但转为可被玩家直接控制的采集单位。

### 15.10　重开与再战

一局结束时，结算面板必须提供三个出口（P0），主菜单另提供一个入口（P1）。所有出口都不得丢失当前设置。

| 入口名称 | 位置 | 行为 | 快捷键 | 保留项 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| 重开本局 | 结算面板第一按钮 | 用完全相同的设置与种子重新开局 | R | 地图、种子、难度、阵容、源质、速度、迷雾、混沌巢穴、人口 | P0 |
| 换图再战 | 结算面板第二按钮 | 返回遭遇战设置界面，保留全部设置项但重掷种子 | M | 全部设置项，仅种子变化 | P0 |
| 观看录像 | 结算面板第三按钮 | 进入观战/演示模式并从头播放本局录像 | V | 本局全部设置 | P2 |
| 返回主菜单 | 结算面板第四按钮 | 丢弃本局，返回主菜单 | Esc | 无 | P0 |
| 继续战役 | 战役结算面板专属 | 载入下一关，难度沿用本关选择 | N | 难度、速度 | P0 |
| 重玩战役关 | 战役结算面板专属 | 重开当前关卡，难度沿用本关选择 | R | 难度、速度 | P0 |

重开本局必须是**确定性一致**的（P0）：只要 `(mapId, seed, size, difficulty, playerFaction, aiFaction)` 六元组不变，重开后的地图逐格一致（含 `terrain`、`height`、`essence`、`chaosLairs` 四处）、混沌巢穴的守护单位配置一致、AI 的随机决策序列一致。实现方式是在开局时把六元组与一个全局 PRNG 种子写入一局唯一的 `matchSeed`，重开时复用同一 `matchSeed`，而不是重新取系统时间。**注意**：混沌巢穴的守护单位虽然由 `map` 流生成，但它们的**行为**由 `ai` 流的独立子流驱动（第 16 章的「随机流的分流」），因此地图重开一致不等于战斗结果一致——只有 `matchSeed` 与命令流同时复用，整局才会逐位重现。

录像回放入口只列入口，细节不展开（P2）：入口共三处，分别是结算面板的「观看录像」按钮、主菜单「演示」模式下的「载入录像」选项、以及战役关卡的「回放上一局」按钮。录像文件格式为「种子加输入指令流」，指令流按 tick 记录双方的全部玩家指令与 AI 决策摘要，回放时以 20 Hz 逐 tick 重放并断言世界状态哈希一致，哈希不一致时在时间轴上标记「不同步」节点并继续播放。**录像不记录奴隶的微观指令**——奴隶由预设 AI 驱动，其行为完全由世界状态与 `ai` 流决定，因此只要初始状态与命令流一致，奴隶的每一次采矿路径都会逐位重现。
